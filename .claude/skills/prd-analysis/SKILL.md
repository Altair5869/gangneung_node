# PRD Analysis — 강릉 노드 요구사항 분석 절차

코드부터 작성하면 나중에 "이게 데이터 규칙 위반인 줄 몰랐다"는 재작업이 생긴다. 요구사항 단계에서 걸러내는 게 개발자와 QA 양쪽의 시간을 아낀다.

## Step 1: 기획서 위치 확인 (지어내지 않기)

`Gangneung_Node_Plan.md`는 `CLAUDE.md`에 "상위 폴더 `GangneungNode/`에 위치"라고 문서화돼 있지만, 실제로 그 위치에 없을 수 있다 (프로젝트 폴더가 이동/재구성됐을 가능성). 먼저 찾아본다:

```
find ~/Desktop -maxdepth 3 -iname "*Gangneung_Node_Plan*"
```

찾으면 읽고, 못 찾으면 "기획서 미발견"으로 기록하고 `CLAUDE.md` + `docs/DATA_STATUS.md` + `docs/AGENT_DESIGN.md`만으로 분석을 진행한다. 없는 파일 내용을 추측해서 채우지 않는다.

## Step 2: 알려진 기획서-구현 불일치 확인

`CLAUDE.md`에 이미 기록된 불일치: 기획서엔 "LLM(OpenAI/Gemini) 연동"이라 적혀 있으나 실제 구현은 Claude API(`lib/ai.ts`). 이번 요청이 이 불일치 영역과 관련 있으면 언급한다. 분석 중 새로운 불일치(기획서 vs `docs/`, `CLAUDE.md`)를 발견하면 같은 형식으로 기록한다.

## Step 3: 데이터 규칙 충돌 여부 판단

요청이 아래 필드를 건드리면, 요구사항으로 만들기 전에 `CLAUDE.md`의 "데이터 관련 필수 규칙"과 충돌하는지 먼저 확인한다:

| 필드 | 확정된 제약 |
|---|---|
| `wifi.available` | 실측 없으면 `null`. `true`/`false` 하드코딩 금지 |
| `wifi.speedMbps` | 수집 자체 안 함. "와이파이 속도 표시" 같은 요청은 요구사항化하지 않고 왜 안 되는지 설명 |
| `power.level` | `"충분함" \| "제한적" \| "없음" \| null` 3단계. boolean으로 되돌리는 요청은 거부 |
| `noise` | `"언급됨-조용함" \| "언급됨-시끄러움" \| "언급없음"` 신호. "조용한 곳만 정확히 걸러줘" 같은 확정 사실 취급 요청은 신호 기반 한계를 사용자에게 먼저 설명 |
| `barrierFree` | 실데이터 — 검증 조건에 자유롭게 사용 가능 |

충돌하는 요청이면 요구사항 문서에 "제약 위반 — 진행 불가/대안 필요"로 명시하고, 대안(예: 신호 기반으로 표현 완화)을 제시한다.

## Step 4: 요구사항 문서 작성

`.claude/_workspace/01_pm-analyst_requirements.md`에 아래 템플릿으로 작성한다. 간단한 버그 수정은 전체 섹션을 다 채우지 않아도 된다 — 영향 범위와 완료 기준만으로 충분하면 그렇게 한다.

```markdown
# 요구사항: {요청 한 줄 요약}

## 요구사항 목록
1. ...
2. ...

## 영향 범위
- 파일: {app/api/... , lib/..., components/...}
- 데이터 필드: {건드리는 WorkSpot/LifeSpot 필드, 없으면 "없음"}

## 데이터 규칙 체크
- {Step 3에서 확인한 충돌 여부. 없으면 "해당 없음"}

## 완료 기준 (Acceptance Criteria)
- [ ] ...
- [ ] ...

## 기획서 불일치 발견 사항
- {있으면 기록, 없으면 생략}

## 공모전 일정 리스크
- {1차 서류 마감 9/21 16:00 관련 리스크가 있으면 기록, 없으면 생략}
```

## Step 5: developer에게 전달

문서 작성 완료 후 SendMessage로 developer에게 경로와 핵심 요약(요구사항 목록 + 완료 기준)을 전달한다. 전체 문서를 다시 채팅에 붙여넣지 않는다 — 파일 경로로 충분하다.
