# 커뮤니티 검증 체크인 기능 설계 (2026-08-11)

## 배경 및 목적

`docs/DATA_STATUS.md`에 이미 명시적으로 기록된 미해결 약점: `WorkSpot.wifi.available`/`power.level`은 `VERIFIED_SPOTS`(전화·방문으로 실측한 24곳)에서만 진짜 값을 갖고, 그 밖의 스팟(관광공사/카카오 API로 실시간 유입되는 나머지 200여 곳)은 전부 `null`(미확인)이다. 전화 실사는 스케일이 안 되는 방식이라 24곳에서 더 늘어나지 않고 있다.

이 기능은 실제 방문자가 현장에서 wifi/콘센트 상태를 짧게 체크인하도록 해서, `VERIFIED_SPOTS`(팀 실측)와 `null`(미확인) 사이에 **세 번째 신뢰 계층("커뮤니티 확인됨")**을 만든다. 목적은 두 가지다: (1) 실사용자에게 실질적 가치(더 많은 스팟의 wifi/콘센트 정보), (2) 이 프로젝트가 일관되게 지켜온 "확정 아닌 걸 확정처럼 표기하지 않는다"는 데이터 정직성 원칙을 커뮤니티 데이터에도 동일하게 적용하는 사례를 만들어 공모전 심사 서사를 강화.

## 범위

**포함:**
- NextAuth 기반 Google 소셜 로그인(카카오/네이버는 프로바이더 승인 완료 후 추가 — 별도 후속 작업)
- Upstash Redis에 체크인 레코드·집계값 저장
- 체크인 제출 UI(`/spots/[id]`), 위치 기반 제출 가능 여부 판정(GPS + 하버사인 거리)
- Wilson score interval 기반 "커뮤니티 확인됨" 승격 판정
- `/spots`, `/spots/[id]`에 커뮤니티 신뢰도 배지 노출
- `@upstash/ratelimit`을 이용한 계정/기기당 체크인 속도 제한

**제외 (비목표, 이번 라운드 범위 아님):**
- `validateRoute`/AI 큐레이터 pass/fail 검증에 커뮤니티 데이터 반영 — 신뢰도 계층을 먼저 검증할 시간이 필요해 다음 라운드로 미룸(D-② 라운드가 라이프스팟 색인을 검증 로직에 바로 안 태우고 별도 라운드로 나눴던 것과 같은 이유)
- `noise` 필드 체크인 — 이미 네이버 검색 API 신호로 관리 중, 중복 방지
- 자유 텍스트 코멘트 — 구조화된 값(wifi/power)만 받기로 결정, 임베딩 기반 스팸 탐지는 그에 따라 불필요해짐
- 카카오/네이버 로그인 — Google 로그인으로 기능이 동작하는 걸 먼저 확정한 뒤, 프로바이더 승인 완료 시 추가(마감 리스크 관리)
- Spring Boot/Kotlin 백엔드 — 검토 후 기각. 이유: (1) 이 기능 규모 대비 신규 언어·별도 배포처·DB·인증을 전부 새로 구축해야 해서 1.5~3주 소요 추정(OAuth 프로바이더 승인 대기가 가장 큰 변수), (2) 마감(9/21) 리스크가 이미 `CLAUDE.md`가 FastAPI 분리를 기각한 것과 같은 이유로 더 크게 적용됨, (3) 이 프로젝트의 심사 서사(Next.js + LangGraph AI 에이전트 설계 + 데이터 정직성)와 무관한 스택이 끼어들어 서사가 흐트러질 위험. Next.js API Routes + Upstash Redis + NextAuth로 대체

## 아키텍처

- **DB**: Upstash Redis(`@upstash/redis`) — 이미 Upstash Vector를 쓰고 있어 같은 벤더, 신규 계정 설정 부담 없음. 새 서버 배포 없음, 기존 Next.js/Vercel 배포 구조 그대로 유지.
- **인증**: NextAuth, Google 프로바이더로 시작. 세션은 NextAuth 기본 JWT 세션 사용(별도 세션 스토어 불필요).
- **속도 제한**: `@upstash/ratelimit`(공식 SDK)로 사용자 ID + IP 조합 기준 슬라이딩 윈도우 제한(예: 스팟당 24시간에 1회, 계정당 1시간에 N회) — 코드 몇 줄로 처리, 새 인프라 불필요.
- **위치 검증**: 브라우저 Geolocation API로 좌표를 받아 `calculateHaversineDistance`(`lib/ai.ts`, 기존 함수 재사용)로 스팟 좌표와의 거리를 계산. 반경(예: 100m) 밖이면 제출 차단. AI 에이전트 설계 규칙 2("거리 검증은 하버사인 공식")와 동일한 계산 방식을 재사용해 이 프로젝트 전체의 거리 계산 로직을 하나로 유지.

## 데이터 모델 (Upstash Redis)

```
checkin:{spotId}:{userId} → { wifiAvailable: boolean, powerLevel: "충분함"|"제한적"|"없음", submittedAt: ISO8601 }
  # 사용자당 스팟당 최신 체크인 1건만 유지(덮어쓰기). TTL 없음(과거 체크인은 집계에 계속 반영).

checkin:agg:{spotId} → {
  wifiYes: number, wifiNo: number,
  powerCounts: { 충분함: number, 제한적: number, 없음: number },
  totalCheckins: number
}
  # 체크인 제출/수정 시 원자적으로 갱신(Redis INCR/HINCRBY)
```

`wifiYes`/`wifiNo`, `powerCounts`는 "가장 최근 상태"가 아니라 **누적 카운트**로 관리한다 — Wilson score interval 계산에 표본 크기가 필요하기 때문. 한 사용자가 체크인을 갱신하면 이전 값을 빼고 새 값을 더하는 방식으로 카운트를 유지한다(단순 append-only가 아님, 중복 계정의 과대표집 방지).

## 신뢰도 승격 로직

`wifiYes`/`(wifiYes+wifiNo)` 비율에 Wilson score interval(95% 신뢰수준)의 **하한**을 적용해, 표본이 적을 때 우연히 높게 나온 비율을 과신하지 않는다. 하한이 임계값(예: 0.6) 이상이면 "커뮤니티 확인됨(wifi 있음)"으로 승격, 그 미만이면 여전히 "정보 부족"으로 표시(체크인이 있어도 확정 배지 없음). `power.level`은 최빈값 방식으로 승격 여부를 판정하되 마찬가지로 최소 표본 크기(예: 3건) 미달 시 미확정 유지.

이 임계값(신뢰수준, 최소 표본 크기)은 구현 단계에서 실제 값 분포로 재검토 가능 — D-② 라운드가 bin width를 실측으로 정한 것과 같은 방식으로, 초기 배포 후 실제 체크인 분포를 보고 조정할 여지를 남긴다.

## UI 노출

- `/spots/[id]`: 무장애 5개 필드 배지 옆에 "커뮤니티 확인됨(N명 응답)" 배지 추가, `VERIFIED_SPOTS`(실측) 배지와는 **다른 스타일**(예: 실측은 실선, 커뮤니티는 점선 테두리 — 옵션 C 라운드가 소음 신호와 확정 사실을 시각적으로 구분한 것과 동일 원칙)로 신뢰도 차이를 명확히 표시.
- `/spots/[id]`에 로그인 상태면 "체크인하기" 버튼 노출, 위치 반경 밖이면 비활성화 + 이유 안내.
- `/spots` 목록 카드에는 커뮤니티 확인 배지만 축약 표시(상세 수치는 상세 페이지에서만).
- `RouteVerificationCard`(AI 큐레이터 결과 화면)는 **이번 라운드에서 변경하지 않음** — 비목표 참고.

## 데이터 규칙 준수 체크

- `wifi.speedMbps`는 체크인 대상에 포함하지 않는다(규칙 2 유지).
- `noise`는 체크인 대상에서 제외(규칙 3, 네이버 API 신호 체계와 중복 방지).
- 커뮤니티 데이터는 `VERIFIED_SPOTS`(실측)와 동일한 신뢰도로 표기하지 않는다 — 별도 배지 스타일, "몇 명이 확인함"이라는 표본 크기를 항상 함께 노출해 확정 사실처럼 보이지 않게 한다.
- `validateRoute`의 기존 6개 체크는 이번 라운드에서 무변경.

## 리스크

- **OAuth 승인 대기**: Google은 즉시 발급되지만 카카오/네이버는 비즈니스 등록·검수가 필요할 수 있어 일정이 불확실 — 이번 라운드는 Google만으로 기능을 완결하고, 카카오/네이버는 승인 완료 시 별도 후속 작업으로 추가.
- **콜드스타트(빈 상태) 문제**: 배포 초기엔 체크인이 거의 없어 배지가 거의 안 뜬다 — 데모/심사 시연 시 안내 문구("아직 커뮤니티 데이터가 부족합니다, 첫 체크인을 남겨보세요" 등)로 빈 상태를 정직하게 보여줄 것 권장. 가짜 시드 데이터로 채우지 않는다(데이터 정직성 원칙 위반).
- **위치 검증 실패 시나리오**: 브라우저가 위치 권한을 거부하면 체크인 자체를 막을지, 낮은 신뢰도로 허용할지는 구현 단계에서 재확인 필요(현재 설계는 "막는다"를 기본값으로 함).
